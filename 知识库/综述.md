因此下文的原则是：**凡跨簇的呼应，一律标为"本库编译者的观察"；凡来源间真实的互证，才写成互证。**

## 整体图景

### 主体簇：一个支付系统的纵向链路与横向底座

- **纵向**：[[支付网关]] 所在来源处理交易完成**之前**——渠道可用性、终端适配、回调一致性；[[清结算]] 所在来源处理交易完成**之后**——清分、计费、结算、入账。两篇摘要页对这条前后段边界的表述完全一致，且指明接口：网关推进出的最终支付状态，就是清结算侧"交易流水接入"的输入。
- **横向**：[[分库分表]] 与 [[跨库 Join]] 所在来源构成数据底座——业务做大后必须拆分，拆分牺牲关联能力，再用五种方案换回来。

### 工程实践簇：四条互不相交的线

除 Spring Boot 的三篇彼此构成"自动装配机制 / Starter 交付 / API 版本路由"的松散簇外，这一批内部联系很弱：

- [[摘要/DDD 分层到六边形架构]] 谈**边界怎么划、依赖往哪指**，是架构观；
- [[摘要/Spring Boot 自动装配原理]] 与 [[摘要/Spring Boot Starter 全解析]] 谈**框架怎么按条件装配、怎么把装配交付出去**，由 [[自动装配]]、[[Starter]]、[[条件注解]] 三页承载；
- [[摘要/Spring Boot 4 API 版本控制]] 谈**接口契约如何随版本分化共存**，与本库其余任何页面**无概念重叠**；
- [[摘要/美团数据库容量评估系统]] 谈**集群还能扛多少、变更安不安全**。

**其中唯一值得记录的真实关联**：[[摘要/DDD 分层到六边形架构]] 只在举例时触及支付域（以"改支付会碰到账户、订单、库存的纠缠"说明三层架构的纠缠症状、限界上下文示例表含"支付"一行、以跨账户转账演示领域服务）——**这些是示例，不是论述**，原文从未讨论清结算或支付网关本身。

## 反复出现的问题

1. **局部故障不得扩散**。[[摘要/支付系统技术决策]] 的原话是"不让一个局部故障演变成整个支付系统的故障"，实例是渠道混部时慢请求占满线程池拖垮所有渠道；这正是 [[摘要/MIT 6.824 分布式系统]] 所述 partial failure 的工程化表达。两来源从课堂与生产一致指向同一件事。

2. **方案皆代价，按规模/场景选型**。这条在主体簇内本是**三篇互证**：支付篇承认"多拆一个服务、多加一层网关"是平时的成本、故障时的价值；[[摘要/跨库 Join 方案]] 明言"没有银弹"、小团队上数据异构"大概率死于运维"；[[摘要/清结算模块设计]] 论证规则无法跨业务形态通用。

   **新增批次在这条原则上高度收敛，但属编译者观察而非来源互证**：[[摘要/DDD 分层到六边形架构]] 的判据是「复杂在领域时用 DDD 管理复杂度；简单在数据表时别过度设计」；[[摘要/Spring Boot Starter 全解析]] 记下 Starter 的代价是"每个 Starter 的 AutoConfiguration 都要被评估"；[[摘要/美团数据库容量评估系统]] 则把超载标准交给用户自己的告警策略，而非系统内置阈值。**四簇从不同层面给出同一种拒绝一刀切的态度**——但四篇原文彼此从未相遇，不应据此声称它们互相印证。

3. **对账是不可省略的兜底**。[[摘要/清结算模块设计]] 把对账对平列为前提、准确率逼近百分之百；[[摘要/跨库 Join 方案]] 把另建对账系统列为数据异构的固有成本。两个不同角度（资金账务、查询架构）得出同一结论：**只要数据被拆开或复制，对账就省不掉**。

4. **"结论会腐烂"这件事开始被正面处理**。这是本批次带来的**新主题**，此前四篇均未涉及：[[摘要/美团数据库容量评估系统]] 专门设计了"评估结果保鲜"机制——比对配置快照差异、标记失效、设过期时间自动重评。它与 [[摘要/MIT 6.824 分布式系统]] 的"部分失败"没有理论关联，**而是工程上对"结论有时效"的承认**，本库把它记为一条独立观察。

## 互相支撑的结论

- 交易段与资金段的链路边界及衔接接口（支付状态 → 流水接入），两篇摘要页互证；
- "局部故障隔离"既是支付篇的架构动机，也与 6.824 的部分失败概念吻合——工程直觉与课程理论相互背书；
- "先定用户可覆盖的默认值，再让用户覆盖"：[[自动装配]] 的"用户优先"与 [[Starter]] 的 `@ConditionalOnMissingBean` 是两篇摘要页在**同一主题上的互补**（一篇讲机制，一篇讲交付），属真实互证。

## 一处张力（并列，不抹平）

> [!contradiction] 跨库 Join 方案 vs 清结算模块设计
> 关于"不一致可以容忍多久"，两篇摘要页给出了差别巨大的标尺：
> [[摘要/跨库 Join 方案]]：冗余字段方案**接受几小时异步补偿的最终一致**，前提是展示型字段（昵称、商品名）；
> [[摘要/清结算模块设计]]：资金账务侧**对账必须对平、准确率逼近百分之百**，没有容忍窗口。
> 当前状态：已解决——两者针对的数据语义不同（展示字段 vs 资金字段），并非同一命题的冲突，各自的标尺在其语义下均成立，故不构成事实矛盾。

但跨库 Join 篇自己在"值得追问"里留下了缺口：若冗余的是金额或状态类字段，几小时的容忍窗口是否还成立？原文未讨论。本库尚无资料正面回答"支付数据从展示字段跨到资金字段时一致性要求如何换挡"，这是一个值得在后续 ingest 中留意的问题。

## 一处未解决的冲突

> [!contradiction] Spring Boot Starter 全解析 vs Spring Boot 自动装配原理
> 关于 **Spring Boot 3.x 下 `spring.factories` 中的 AutoConfiguration 条目是否仍然有效**，两来源结论相反：
> [[摘要/Spring Boot Starter 全解析]] 称「旧文件格式**仍然兼容**但已被废弃」；
> [[摘要/Spring Boot 自动装配原理]] 称「**移除了**支持」「如果只配置 `spring.factories`，自动配置将**不生效**」。
> 当前状态：**未解决**。无第三方来源可裁决，本库不为任一来源背书。实践建议以 `.imports` 为唯一写法——两种说法在这一点上不冲突，且在"不生效"为真时是唯一安全的做法。
> 详见 [[自动装配]] 页的完整 callout。

## 结论

主体簇内部高度互洽（除上述展示字段/资金字段一处张力，已判为语义差异）；新增四个主题簇**各自成立，但与本库主体尚无原文层面的交集**——这是当前最明确的摄取方向：若出现同时谈"支付系统架构演进"或"DDD 应用于交易域"的来源，将成为连通两簇的第一条真实边。

跨全部 10 篇仍可提炼的共同原则是：**隔离局部故障、按规模付代价、用对账兜底一切数据分裂**——并新增一条：**给出的结论要能随环境变化而失效重评**。
