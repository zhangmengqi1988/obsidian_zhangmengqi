自动装配指 Spring Boot **根据 classpath 中的依赖、应用环境（Web/非 Web）、配置属性等条件，自动向 IoC 容器注册 Bean** 的机制。它常被误解为"帮你写配置"，实际是**按条件决定装不装**——本页记录它的判定依据、执行链路与失效排查，落点是"什么时候会被它绕过去"。

## 核心判据：用户优先

一条原则解释了绝大多数"我配了为什么不生效"和"我没配为什么生效了"：

> 约定大于配置，按需装配，用户优先

两个方向的操作后果不对称：

| 想做的事 | 正确做法 | 常见错误 |
|---|---|---|
| 覆盖自动配置的 Bean | **自己定义一个同类型 Bean** | 去改自动配置类源码 |
| 让自动配置真正生效 | 先查是否撞上 `@ConditionalOnMissingBean` | 反复检查自己的配置写法 |

`@ConditionalOnMissingBean` 是这条原则的机械实现：**用户没配，才自动配**。因此排错时应先看容器里是不是已经有了同类型 Bean，而不是先看属性文件。

## 执行链路

```
@SpringBootApplication
  └─ @EnableAutoConfiguration            （= @AutoConfigurationPackage + @Import(...)）
       └─ @Import(AutoConfigurationImportSelector.class)
            └─ selectImports() → getAutoConfigurationEntry()
                 0. isEnabled() 前置检查（enable=false 直接返回 NO_IMPORTS）
                 1. getCandidateConfigurations  加载候选
                 2. removeDuplicates            去重
                 3. filter                      排除列表 + 条件注解过滤
                 4. sort                        拓扑排序
```

入口**不是注解本身**，而是 `@Import` 引入的选择器——Spring Boot 复用了 Spring 既有的"批量导入注册 Bean"扩展点。

**第 2 步为什么用 `LinkedHashSet`**：去重的同时**保持原始加载顺序**，因为第 4 步的拓扑排序依赖这个顺序的稳定性。

## 第 4 步：顺序由拓扑排序决定

**"写得越靠前越先执行"是错的。** 依赖关系用三个声明表达——`@AutoConfigureOrder`（数值）、`@AutoConfigureBefore`、`@AutoConfigureAfter`——由拓扑排序（Kahn）求解。

原文示例：`A(@AutoConfigureOrder(10))`、`B(20)`、`C(after A, 30)`、`D(before B, 25)` → 结果 `A → D → B → C`。

一个易被忽略的实践后果：**自定义 Starter 的自动配置类若要依赖他人的 Bean，必须显式声明 `@AutoConfigureAfter`**，否则顺序不确定。

## 判定的执行时机与底层抽象

条件判断的三层结构是：Spring Framework 的 `Condition` 接口 → Spring Boot 的 `SpringBootCondition` 抽象类 → 返回值 `ConditionOutcome`（含 `boolean match` 与 `ConditionMessage message`，即"匹配/不匹配的原因说明"）。

`SpringBootCondition.matches()` 的流程为：记录匹配追踪（供 debug 日志与 auto-configuration report 使用）→ 调用子类 `getMatchOutcome()` 做实际判断 → 记录到 `ConditionEvaluationReport`。**条件评估发生在容器启动的 BeanDefinition 注册阶段**，不是编译期。具体条件维度见 [[条件注解]]。

## 排查：读报告，不要读源码猜

`debug=true` 或启动参数 `--debug` 输出 **CONDITIONS EVALUATION REPORT**，分两段：

- **Positive matches** —— 条件满足、装配了的
- **Negative matches** —— 条件不满足，**并给出原因**

Actuator 侧等价入口：`management.endpoints.web.exposure.include=conditions` 后访问 `GET /actuator/conditions`。

## 排除自动装配的三种方式

| 方式 | 写法 |
|---|---|
| `exclude` | `@SpringBootApplication(exclude = XxxAutoConfiguration.class)` |
| `excludeName` | 同上，传字符串类名（用于类不在 classpath 时） |
| 配置 | `spring.autoconfigure.exclude` |

三者**效果合并**而非互斥，原文给出的优先级为 `exclude` > `excludeName` > `spring.autoconfigure.exclude`，**所有被排除的类都不会被加载**。

## "扩展"与"接管"的分界线

`WebMvcAutoConfiguration` 给出了一条通用判据，值得迁移到其他自动配置类上理解：

- 用户只实现 `WebMvcConfigurer` 接口（**扩展** MVC 配置）→ 自动配置**仍然生效**，两者叠加；
- 用户继承 `WebMvcConfigurationSupport`（**完全接管** MVC 配置）→ 自动配置**不生效**。

即：**接口 = 加东西，基类 = 换实现**。想要自动配置的默认值就实现接口，想要全部自己来才继承基类。

## 一处未解决的来源冲突

> [!contradiction] Spring Boot Starter 全解析 vs Spring Boot 自动装配原理
> 关于 **Spring Boot 3.x 下 `spring.factories` 中的 AutoConfiguration 条目是否仍然有效**，两来源给出了不同结论：
> [[摘要/Spring Boot Starter 全解析]] 称「Spring Boot 2.7 之前使用 `META-INF/spring.factories`，Spring Boot 3.x 已迁移到新的 `.imports` 文件。**旧文件格式仍然兼容但已被废弃**」；
> [[摘要/Spring Boot 自动装配原理]] 称「Spring Boot 3.x **移除了**对 `spring.factories` 中 AutoConfiguration 的支持，必须使用新格式文件」「**如果只配置 `spring.factories`，自动配置将不生效**」。
> 前者指"仍兼容"，后者指"不生效"——对同一版本区间给出了相反结论，且症状描述（静默不生效 vs 仍可用）在实践中可直接区分，不是措辞差异。
> **当前状态：未解决。** 本库无第三方来源可裁决。一条**未经证实的**消解方向是：「框架仍会读取 `spring.factories` 这个文件格式」与「其中的 AutoConfiguration 条目是否仍被消费」可能是两件事——但这只是假设，**两来源均未把这一层讲清，本库不为任一来源背书**。
> 实践建议：**以 `.imports` 为唯一写法**。两种说法在这一点上不冲突，且在"不生效"为真时是唯一安全的做法。
