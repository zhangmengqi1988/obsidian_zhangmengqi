容量评估回答两个问题：**这个集群还能扛多少**，以及**我负责的上百个集群现在各在什么水位**。**首现于 [[摘要/美团数据库容量评估系统]] 单一来源，故本页为 stub**。该来源把回答拆成三条递进链：[[流量回放]]（变更做了会怎样）→ **容量上探**（最多能扛几倍）→ **容量运营**（周期观测与治理）。

## 定义与出处

来自 [[摘要/美团数据库容量评估系统]]：

### 容量上探——探测上限

- **超载标准沿用用户自己的告警策略**：「用户根据业务场景为 RDS 集群设置相应的告警策略，集群出现告警表明集群超载」——**代价是结论口径随人的配置而变**。
- **两阶段搜索，不是单一策略**：「快速上探期」用**指数加压**快速探测告警触发边界以定位区间；「精确校准期」基于"触发告警的最小速度"与"未触发告警的最大速度"两个边界值做**二分计算**，达到预设精度后自动终止。
- **倍速的本质是压缩时间轴**：「通过压缩 SQL 执行间隔，提升单位时间内的请求密度」，公式为 `planDelta = originalDelta / 回放速度`；沙盒配置**要求与线上集群保持一致**才保证上探结果真实。

### 容量运营——把结论变成指标

- **水位口径**：「**容量使用水位 = 线上集群 QPS / 上探评估读写 QPS 上限**，默认健康水位区间 **[30%, 50%]**，小于区间下限表示容量冗余，超过区间上限则容量不足（无法满足业务常态化 **2 倍**流量的承载需求）」。**50% 上限不是随意的**——它对应"留一倍冗余扛常态化 2 倍流量"。
- **评估结果保鲜**（本页最工程化的一环）：定期比对评估配置快照与线上集群当前配置的差异，若「业务流量模型、硬件配置、版本与参数、告警阈值等配置发生变化」则**标记失效并重新评估**；托管集群的评估结果带**过期时间**，逾期自动重评。**它解决的是"结论会腐烂"这个常被忽视的问题。**

## 与 [[分库分表]] 的关系（易被误读，特别说明）

**本文没有填补 [[分库分表]] 的任何登记缺口**（拆分策略选型 / 扩容 / 全局 ID）——全文未论述分片键选择、分库分表方法论、数据迁移或全局 ID。全文唯一涉及"拆分"的表述在效果展示一节：「按照系统给出的容量建议完成了数据库**扩容拆分**工作」，属**结果描述**，无方法无过程。

两者的真实关系是**问题相邻而层面不同**：分库分表回答"数据该放在几个库里"，本页回答"现有的库还能不能扛住"。本系统产出的**水位与缩扩容节点建议**（含机房分布）是判断是否需要扩容的输入，**但原文并未把它与分库分表这个决策联系起来**。
