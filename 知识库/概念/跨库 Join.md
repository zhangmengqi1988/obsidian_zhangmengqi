跨库 Join 是 [[分库分表]] 的直接代价：表散落在不同机器的不同 MySQL 实例上，跨实例 JOIN 不是性能差，而是**根本无法执行**。分库分表用数据分散换来写入吞吐与单表查询性能，牺牲掉的正是跨表关联能力。解决它的本质是：**用空间、约束或架构换回关联能力，每种方案都有必须讲清的代价**。

## 五种方案与代价

| 方案 | 做法 | 代价 |
|---|---|---|
| 绑定表 | 主从表使用完全相同的分片键与分片算法（如订单表与订单详情表均按 user_id % 64 分片），关联数据天然同库，中间件把 JOIN 改写为单库内执行 | 分片策略被绑死（一张表改分片键则绑定关系全废）；只解决一对一场景 |
| 广播表 | 数据量极小、几乎不更新的字典/配置/地区表在每个库实例放完整拷贝，写入由中间件广播 | 写入放大；频繁更新的小表用广播表会变成一致性噩梦 |
| 冗余字段 | 建单时直接把 user_name、product_name 写入订单分表，查询零 Join | 一致性——源字段变更本身又成了跨库更新；通常接受短暂不一致、几小时内异步补偿（弱一致） |
| 应用层关联 | 分页查订单 → 提取 ID 集合 → 批量 IN 查另一库 → 内存组装，用四次查询（四个 RTT）换跨库能力 | 大忌是循环逐条查询的 N+1，必须用批量 IN |
| 数据异构 | 经 Binlog CDC 或应用层双写把数据实时同步到 Elasticsearch / ClickHouse / 聚合 MySQL 查询库，交易库只管写入与主键/分片键查询 | 链路上每一步都是坑：同步延迟（秒到分钟级）、消息丢失（Canal 宕机/Kafka 丢消息/ES 写入失败）、DDL 变更导致 mapping 漂移、必须另建对账系统 |

## 一致性阶梯

绑定表与广播表强一致 → 应用层关联强一致 → 冗余字段弱一致 → 数据异构最终一致。复杂度与核心代价随能力递增，没有银弹：4 张表的小团队用应用层关联就够了，64 张表的大流量必须上 ES。

## 数据异构的适用门槛

查询维度超过 5 个、有全文搜索需求、日均查询量百万级，三者具备才值得上；"4 张表、日活几千、两三人的团队上这套，大概率死于运维"。这与 [[支付网关]] 所在来源的方法论一致：方案皆代价、按场景选型，反对无条件上重型方案。

## 对账是兜底动作

数据异构要求"另起一套对账系统，定期全量比对、发现不一致要补偿"。这与 [[清结算]] 把"对账必须对平"列为前提相互印证——只要数据被拆开或复制，对账就省不掉。两个来源从查询架构与资金账务两个不同角度指向同一结论。
