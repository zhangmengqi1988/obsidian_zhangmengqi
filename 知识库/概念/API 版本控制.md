API 版本控制指**同一业务接口随不兼容变化而分化出多套响应契约**时的路由与共存机制。**首现于 [[摘要/Spring Boot 4 API 版本控制]] 单一来源，故本页为 stub**。

## 定义与出处

来自 [[摘要/Spring Boot 4 API 版本控制]]：

- **旧做法的根本问题不是丑，而是绑死了两种版本**：原文「以前按照 /v1、/v2 整套复制 Controller，本质上把『**应用版本**』和『**单个接口版本**』绑得太死」——接口版本的演进节奏与应用部署版本本不必一致。
- **新做法的实质是版本成为请求映射的一部分**：两个方法同名同路径，仅靠 `version` 属性区分；未发生分化的方法不写 `version`。
- **⚠️ 最关键的选型判据是"DTO 分版本、Service 不跟版本走"**：原文反对在老对象上追加字段「然后希望老客户端『忽略它不认识的字段』」，也明确反对 `OrderV1Service / OrderV2Service / OrderV3Service` 这类切分——「除非两个版本的业务规则真的已经不同」。
- **默认版本是迁移窗口的机制**：「如果升级后强制要求每个请求都必须带版本号，这批客户端当天就全挂了」。
- **存量约定不必推翻**：版本来源可选 Header、URL Path Segment、Query Parameter；「如果 API 已经公开出去……为了换一个 Spring 新功能把 URL 全改掉，反而没有必要」。
