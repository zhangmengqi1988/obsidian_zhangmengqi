流量回放指**录制线上真实流量、在隔离环境中重放**，用以验证变更效果或探测系统极限。与全链路压测的区别在于**录制对象与施压层级**：本文方案的录制对象是**数据库层的全量 SQL**，施压也只针对数据库这一层。**首现于 [[摘要/美团数据库容量评估系统]] 单一来源，故本页为 stub**。

## 定义与出处

来自 [[摘要/美团数据库容量评估系统]]：

- **它替代的是什么**：原文认为**指标计算**的问题在于「流量与相关指标不是严格的线性关系，通过指标预测容量上限的准确性不高」；**全链路压测**的问题在于「数据库流量会受压测场景复杂性、样本丰富度等多种因素影响，导致难以完全拟真，同时业务服务接入压测有一定的改造成本」。流量回放走"线上真实 SQL + 只压数据库"这条路。
- **四个流程**：流量采集 → 流量处理 → 流量回放 → 数据分析与报告。
- **⚠️ 回放单元的粒度由被压目标的语义决定**（本页最值得记住的一条）：「主库采用**事务维度聚合**的方式处理 SQL，将同一事务内的多个 SQL 操作整合为一个执行单元，保证数据操作的一致性与执行效率；从库采用**独立 SQL 维度**处理，保证 SQL 独立执行更好模拟高并发读场景。」
- **沙盒环境的两要件是快照与变更窗口**：快照「通过数据备份构建流量录制时间起点时的全量数据快照」保证增量数据匹配；随后提供「**运维变更窗口**」，用户在其中完成 MySQL 版本升级、参数修改、表结构变更等模拟操作——**没有变更窗口，回放只能测"现状"而不能测"变更后"**。

技术组件：MTSQL 内核采集 → rds-agent → Kafka → Flink 清洗 → ClickHouse 存储；sql-log agent 按主从角色扫描并固化为流量文件 → S3；replay-agent 流式消费并回放，部署于 K8s（每任务独立 Job）。
