以面试三连问（知道方案吗→绑定表用不了怎么办→代价是什么）为线索，系统对比分库分表后跨库 Join 的五种方案，核心结论：跨库 Join 的本质是用空间、约束或架构换回关联能力，每种方案都有必须讲清的代价。

## 关键论点

- 根因：分库分表后表散落在不同机器的不同 MySQL 实例上，跨实例 JOIN 不是性能差而是根本无法执行；分库分表用数据分散换来写入吞吐与单表查询性能，代价是跨表关联能力被牺牲。
- 绑定表：主从表使用完全相同的分片键与分片算法（如订单表与订单详情表均按 user_id % 64 分片），关联数据天然同库，中间件把 JOIN 改写为单库内执行；代价是分片策略被绑死（一张表改分片键则绑定关系全废），且只解决一对一场景。
- 广播表：数据量极小、几乎不更新的字典/配置/地区表在每个库实例放完整拷贝，写入由中间件广播；代价是写入放大，频繁更新的小表用广播表会变成一致性噩梦。
- 冗余字段：建单时直接把 user_name、product_name 写入订单分表，查询零 Join；代价是一致性——源字段变更本身又成了跨库更新，通常做法是接受短暂不一致、几小时内异步补偿（弱一致）。
- 应用层关联：分页查订单 → 提取 ID 集合 → 批量 IN 查另一库 → 内存组装，用四次查询（四个 RTT）换跨库能力；大忌是循环逐条查询的 N+1，必须用批量 IN。
- 数据异构是终极方案：经 Binlog CDC 或应用层双写把数据实时同步到 Elasticsearch / ClickHouse / 聚合 MySQL 查询库，交易库只管写入与主键/分片键查询；链路上每一步都是坑——同步延迟（秒级到分钟级）、消息丢失（Canal 宕机/Kafka 丢消息/ES 写入失败）、DDL 变更导致 mapping 漂移、必须另建对账系统定期全量比对。适用门槛：查询维度超过 5 个、有全文搜索需求、日均查询量百万级；4 张表、日活几千、两三人的团队上这套"大概率死于运维"。
- 一致性阶梯：绑定表与广播表强一致、应用层关联强一致、冗余字段弱一致、数据异构最终一致；复杂度与核心代价随能力递增。

## 与其他资料的关系

- 与 [[摘要/清结算模块设计]] 的直接接口是对账：本篇把"另起一套对账系统，定期全量比对、发现不一致要补偿"列为数据异构的固有成本，而清结算篇把对账对平列为清结算的前提与不可妥协的底线——两者从不同角度指向同一件事：只要数据被拆开或复制，对账就省不掉。
- 决策方法论与 [[摘要/支付系统技术决策]] 呼应：两篇都反对无条件上重型方案、主张按业务规模与故障场景选型，本篇明言"没有银弹，4 张表小团队用应用层关联就够了，64 张表大流量必须上 ES"。

## 值得追问的问题

- 冗余字段"接受几小时最终一致"的前提是展示型字段（昵称、商品名）；若冗余的是金额或状态类字段，这个容忍窗口是否还成立？原文未讨论。
- 数据异构方案里 DDL 变更与 mapping 漂移，原文只点出问题，未给出检测手段与自动修复/告警的工程做法。
- 绑定表"改分片键则全废"，但原文没说生产上真遇到分片键演进（如从 user_id 改为 merchant_id）时的迁移路径是什么。
