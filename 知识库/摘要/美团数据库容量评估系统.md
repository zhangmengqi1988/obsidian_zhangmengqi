## 一句话主旨

美团数据库团队把「集群能扛多少 QPS」和「这次变更安不安全」两个问题，统一收进一条**录制线上真实 SQL → 隔离沙盒回放 → 判断告警边界**的链路，并进一步用容量水位把它变成可周期运营的指标。

## 关键论点

1. **两种常规容量评估方法各有明确的失效边界——这是全文的选型起点。** 原文对**指标计算**的判据是「流量与相关指标不是严格的线性关系，通过指标预测容量上限的准确性不高」；对**全链路压测**的判据是「数据库流量会受压测场景复杂性、样本丰富度等多种因素影响，导致难以完全拟真，同时业务服务接入压测有一定的改造成本」。两者合起来指向本文方案：**用线上真实 SQL 而非构造流量，且只针对数据库这一层压**。

2. **变更风险同理，常规手段也各有盲区。** **固定规则拦截**的问题在于「诸如增加索引、修改字段类型等常规变更通常不会被拦截，这类变更可能导致 SQL 执行效率变差」——即规则拦的是**已知危险动作**，拦不住**安全动作的性能劣化**；**线下测试**的问题是「线下与线上数据存在差异，以及测试不够充分」。本文方案的价值定位正是这两者之间：**用线上数据 + 线上流量的沙盒**。

3. **三条建设要求本身就是三条取舍原则**：数据操作安全（不能影响线上）、评估结果真实（完全拟真的流量与环境）、系统灵活高效（插件化、可被外部系统集成）。第二、三条在实现上是**张力关系**——越拟真越难复用，故用沙盒 + OpenAPI 赋能来化解。

4. **三大核心功能构成一条递进链，而非三个并列工具**：流量回放回答「这个变更做了会怎样」（1 倍速），容量上探回答「最多能扛几倍」（倍速递增），容量运营回答「我负责的上百个集群现在各在什么水位」。原文：「共同构建了从测试到运营的全链路容量管理能力。」

5. **⚠️ 主从两库的流量处理方式不同，这是最容易被忽略的设计判断。** 原文：「主库采用**事务维度聚合**的方式处理 SQL，将同一事务内的多个 SQL 操作整合为一个执行单元，保证数据操作的一致性与执行效率；从库采用**独立 SQL 维度**处理，保证 SQL 独立执行更好模拟高并发读场景。」——**回放单元的粒度由被压目标的语义决定**，不是统一处理。

6. **沙盒环境的两个要件是"快照"与"窗口"**：「通过数据备份构建流量录制时间起点时的全量数据快照，保证回放过程中增量数据的匹配。在回放前提供『运维变更窗口』，在此期间用户可根据需求完成变更模拟操作，如 MySQL 版本升级、参数修改、表结构变更等。」——**变更窗口是这套方案成立的关键**：没有它，回放只能测"现状"而不能测"变更后"。

7. **超载标准不做成系统内置阈值，而是沿用用户自己的告警策略。** 原文：「集群容量与告警紧密相关，用户根据业务场景为 RDS 集群设置相应的告警策略，集群出现告警表明集群超载。」——**代价是结果口径随人的配置而变**（见"值得追问"第 4 条）。

8. **容量上探用两阶段搜索，而非单一策略。** 「快速上探期：系统会持续提升流量回放倍速，通过**指数加压**的方式快速探测系统的告警触发边界，初步确定容量上限范围」「精确校准期：基于触发告警的最小回放速度和未触发告警的最大速度这两个边界值，分析器会进行**二分计算**确定下一次的回放速度。当达到预设精度要求时，评估循环自动终止」。**指数定位区间 + 二分收敛**是本文在此处唯一的算法性内容。

9. **倍速回放的本质是压缩时间轴，公式明确**：原始时间偏移量 `originalDelta`（由 `sqlinfo.BeginAt` 与 `sqlBaseTime` 求差得到）按速度缩放为 `planDelta = originalDelta / 回放速度`。为避免协程在同一时刻同步取 SQL 导致失真，用「SQL 异步预获取」预先分配，并计算距回放开始的实际偏移 `realPassDelta`。

10. **容量运营的定量口径值得单独记住**：「容量使用水位 = 线上集群 QPS / 上探评估读写 QPS 上限，默认健康水位区间 **[30%, 50%]**，小于区间下限表示容量冗余，超过区间上限则容量不足（无法满足业务常态化 **2 倍**流量的承载需求），水位线可按集群维度自行调整。」——**这里的 30%/50% 不是随便定的**：50% 上限对应"留一倍冗余扛常态化 2 倍流量"。

11. **"评估结果保鲜"是整套体系里最工程化的一环**：系统定期比对「评估配置快照与线上集群当前配置的差异」，若「业务流量模型、硬件配置、版本与参数、告警阈值等配置发生变化」则标记失效并重新评估；托管集群的评估结果还带**过期时间**，逾期自动重评。——**它解决的是"结论会腐烂"这个常被忽视的问题**。

12. **两个效果案例的结论方向相反，正好体现两种用途**：表压缩案例中「执行最多的 SQL 耗时从 0.90ms 增加到 0.97ms，未出现明显下降，同时存储占用空间是原来的 40%」→ 判定可接受，实施后「磁盘空间不足问题得到缓解」；降配案例中「流量到达 **6 倍**以上时才触发集群告警，完全满足业务 **2 倍**容量诉求」→ 判定可降配。**前者是"变更够不够安全"，后者是"资源是不是过度配置"。**

## 系统结构（原文明确给出的部分）

```
压测平台（门户）
├─ 核心功能
│   ├─ 流量回放   ← 1 倍速，验证变更
│   ├─ 容量上探   ← 倍速递增，探测上限
│   └─ 容量运营   ← 托管 + 计算 + 自动运维
├─ 对外赋能：OpenAPI（供调度系统集成）
└─ 基础能力：模块化、插件化
```

流量回放的四段流程与关键技术组件：

```
流量采集 Traffic Collect
  MTSQL 内核（全量 SQL 文本 / 事务 ID / 执行耗时）
    → rds-agent → Kafka
    → Flink 清洗链路（过滤出注册集群的 SQL）
    → ClickHouse 存储
流量处理 Traffic Process
  sql-log agent 按主从角色扫描 ClickHouse 全量 SQL
    → 主库：事务维度聚合 ／ 从库：独立 SQL 维度
    → 固化为流量文件 → S3
流量回放 Traffic Replay
  replay-agent 流式消费 S3 流量文件
    → CalcSendTime 时序控制 / 倍速调节
    → 施压部署于 K8s（每任务独立 Job）
    → 沙盒隔离集群（快照 + 变更窗口）
分析 & 报告 Data Analyze & Report
  运行负载指标（CPU busy / Load Average / 慢查询 / 主从延迟）
  SQL 执行信息（每模板执行耗时）
  环境参数（MySQL 核心参数 / 实例机型）
```

容量运营三模块：**评估托管**（准入 → 自动排队执行 → 结果保鲜）、**容量计算**（水位 + 缩扩容建议，含机房分布）、**自动化运维**（一键采纳，可追溯/可观测/可回滚）。

## 值得追问的问题

1. **⚠️ 全文最强的缺口：核心机制几乎全在图里。** 全文 11 张 `wechat_img_*.jpg` 中，**图 2 流量回放流程图、图 3 SQL Replay agent 架构图、图 5 流量上探流程、图 10 容量运营设计架构图**承载的是各模块的内部结构；而 **4.1 业务场景**与 **6.1 业务场景**两节**除一张图外文字层完全为空**。凡结论只存在于图者，本页无法覆盖。

2. **⚠️ 倍速回放的时序控制缺了最后一步。** 原文第 4 步写「系统通过比较 `planDelta` 与 `realPassDelta` 的大小关系来决定 SQL 执行时机」，但**比较之后分别做什么，原文没有写**——是等待、是立即执行、还是补偿，属于原文自身的叙述断裂。图 8「SQL 倍速回放时序控制示意图」可能补足了这一点，但图内内容不在文字层。

3. **倍速是否同比放大并发？** 原文定义倍速是「通过压缩 SQL 执行间隔，提升单位时间内的请求密度」——即只压时间轴。但真实业务流量增长时**连接数通常同步增长**，只压间隔是否等价于真实扩容场景，原文未讨论。

4. **超载判定完全依赖用户配置的告警策略**（见关键论点 7）：这意味着**同一集群由不同人配置告警阈值，会得到不同的容量上限结论**。原文未讲告警策略本身的合理性如何保证。

5. **"评估结果保鲜"的差异比对是否可靠？** 原文列出的比对维度含「业务流量模型」——但流量模型与配置快照不同，不是一个可直接 diff 的对象；它如何被快照化并比对，原文未讲。

6. **规模数据完全缺失**：全文未给出集群数量、SQL 量级、单次回放耗时、ClickHouse 存储规模、K8s 并发 Job 数等任何量化指标，**"支持大规模压测场景"这一说法无数据支撑**。

7. **rds-agent 对线上性能的影响未讲**：「公司自研的 MTSQL 内核采集了全量 SQL 的文本、事务 ID 和执行耗时」——**全量采集本身有成本**，且属第一项要求「数据操作安全」的直接相关面，原文未说明其旁路方式与开销。

8. **容量水位上限 50% 与"常态化 2 倍流量"的换算关系**：50% 恰好对应 2 倍冗余，但 30% 下限的依据原文未讲；且该区间「可按集群维度自行调整」后，是否仍保证容灾要求，原文未讲。
