## 一句话主旨

一篇面向"已有三层架构经验的后端开发者"的 DDD 综述：战略设计管**边界怎么划**，战术设计管**领域模型怎么建**，六边形／洋葱／整洁三种架构则共享同一条纪律——**源码依赖只能向内**。全文的落点始终是选型判断而非实现细节。

## 关键论点

1. **三层架构卡住的根因不是分层本身，而是它不划业务边界。** 原文：「根因通常不是『分层错了』，而是：**技术分层解决的是代码放哪，没有解决业务边界与一致性边界该怎么划。**」这是全文的选型起点——若系统的问题出在边界而非分层，换架构风格才有效。

2. **DDD 的适用判断按"复杂度落在哪"决定，反对一刀切。** 原文：「简单说：**复杂在领域时用 DDD 管理复杂度；简单在数据表时别过度设计。**」这是本文最有操作性的边界判据：DDD 的代价是建模成本，只有当业务规则本身复杂、值得用领域模型承载时才划算。

3. **战略设计先于战术设计**：通用语言（同一限界上下文内文档、对话、代码命名一致）、限界上下文（模型的适用范围，同一词在不同上下文含义可以不同）、上下文映射（上下文之间怎么协作）。子域三分法决定**投入力度**——核心域认真建充血模型，支撑域够用即可，通用域可直接采购。

4. **战术设计的纪律集中在聚合**：「聚合是一组对象及其边界，在**单次事务内**同步维护不变式；**聚合根**是外部**持久引用**与不变式守护的入口」；「**一次事务通常只修改一个聚合实例**（Vernon 的经验法则）」，跨聚合「优先用领域事件等**最终一致**」。

5. **贫血与充血不是道德问题而是适用问题**。原文明确「贫血并非『道德错误』——CRUD 报表可以很合适」；充血模型的价值在于把不变式放进实体方法（`Account.debit(...)` / `Account.credit(...)`），应用服务只做编排与持久化。

6. **六边形／洋葱／整洁二者相似而非等同**。原文：「**Hexagonal（Cockburn）、Onion（Palmero）、Clean Architecture（Martin）共享『源码依赖向内』这条核心纪律**，但历史演进、分层命名与细节不同——相似而非等同。」**落地的判断标准是测试改动量而非包名**：「判断标准不是包名是否时髦，而是：**改数据库时，领域测试是否几乎不用改。**」

7. **边界不等号**：限界上下文是**模型边界**，微服务是**部署与运行边界**——「二者常相关，但不是自动划等号」；拆服务前可「先在模块化单体中划清上下文与包边界」。集成上明确反对**共享可写库**：「问题在共享可写数据模型，而不只是『是否同一台数据库服务器』」；实战最常落地的是「明确谁拥有数据 + 需要时用防腐层隔离外部模型」。

8. **CQRS 应克制使用**：「Fowler 也提醒：多数 CRUD 系统不必默认上 CQRS，应局部、谨慎使用」；入门形态只需「写走应用服务+聚合，读用单独查询方法或只读视图」。

## 与其他资料的关系

**本页与本库已有页面无原文层面的互引关系**——这一点必须讲清，不宜粉饰。原文只在举例时触及支付域（1.2 以「改支付会碰到账户、订单、库存的纠缠」说明三层架构的纠缠症状；2.2 的限界上下文示例表含「支付｜支付单、渠道、回调状态」；3.3 以跨账户转账 debit/credit 演示领域服务）。**这些是示例，不是论述**：原文从未讨论清结算或支付网关本身。

因此本页与 [[清结算]]、[[支付网关]] 的关系是**题材相邻**而非互相印证：DDD 提供的是"支付域该怎么划边界"的建模视角，而本库现有支付类来源提供的是"支付链路本身怎么运作"的领域知识。两者可以互补，但**本库尚无任何来源真正论述过"用 DDD 给支付/清结算建模"**——这是一个真实的缺口，而非既成事实。

值得注意的是方法论上的一致：本文「复杂在领域时用 DDD，简单在数据表时别过度设计」与 [[支付网关]]、[[跨库 Join]] 两页反复出现的「方案皆代价、按规模选型」是同一思维方式。但这属于**本库综合作者的观察**，原文并未与那些来源发生关联。

## 值得追问的问题

1. **限界上下文的具体划分方法论缺失**。原文只给了银行域「示意」切分，并承认「同一个能力对 A 公司可能是通用域，对 B 公司却是核心域」，但如何从实际业务推导出边界、粒度如何判断，原文未讲。
2. **领域事件的投递可靠性未展开**。「跨聚合优先用领域事件等最终一致」——但事件丢失、乱序、重复消费如何保证，原文未讲。
3. **存量迁移路径未讲**。对已腐化的三层大 Service 系统如何渐进重构到六边形包结构，原文仅预告「下一篇将用 Java + Spring Boot 实现一个可运行的账户转账示例：从贫血分层基线出发，落到六边形包结构与充血聚合」。
4. **ACL 与直接同步调用的取舍判据未讲**。2.3 说防腐层最常落地，但何时轻契约直连、何时值得建一层适配，原文未讲。
5. **本剪藏的两处转写缺损**（非原文缺陷，但影响引用）：① 原文六处表格（1.2 症状/典型表现、2.2 上下文、2.3 关系、2.4 子域类型、3.3 领域服务 vs 应用服务、4.4 DDD 元素落点）在微信剪藏中**已被压平成连续文本**，本页的表述据此转写为散文，**不能声称还原了原表结构**；② 文内 8 张 `wechat_img_*.jpg` 示意图仅存引用，图内文字不在文字层。

## 存疑之处

- 原文对 Evans／Vernon／Fowler／Cockburn／Palermo／Martin 的多处观点归属（如「Fowler 也提醒：多数 CRUD 系统不必默认上 CQRS」、`Partnership` 等术语在 *DDD Reference* 中相对 2003 原著有增补）**均无引注、无页码、无链接**，属证据较弱的文献性说法，引用前应回溯原书核实。
- 原文 3.2 写「一次事务**通常**只修改一个聚合实例」时已自加限定语（「仅在确有理由的例外场景打破」），而 3.3 的转账示例仍以单用例串 debit→credit 呈现，原文自注为教学示例。引用该纪律时**必须保留限定语**，否则会误读为生产事务边界。
