响应式：先订阅，上游按需推送数据（推拉结合，有背压契约）；非响应式：主动调用，一次性拉取 / 回调随便推，没有统一的背压协议。**

结合你前面 Reactor、Mono/Flux/Sinks 的背景，拆开讲，避开教科书空话：

## 1. 非响应式（传统 Java：同步、普通回调、Future、Callback）

特点：**调用方主动发起请求，控制权在调用方；没有统一的流契约、没有背压** 分两类：

1. 同步阻塞：`User user = userService.getById(1)` 你发起调用 → 线程卡住等结果 → 拿到返回，完事。
2. 老式异步回调（比如 Netty 原生回调、老 MQ listener、Guava Callback） 你注册一个监听器，**上游想发就发，拼命往回调里塞数据，不管你能不能处理完**。 上游推送速度 > 下游处理速度 → 队列炸、OOM，需要自己手写缓冲、限流、丢弃策略。

> 本质：只是异步，**不是响应式**。异步 ≠ 响应式！ 回调只是 “不阻塞线程”，但缺少一套标准的协商机制。

## 2. 响应式（Reactor / RxJava，遵循 Reactive Streams 规范）

核心是一套**标准化契约**（就是你刚才问的契约式）： `Publisher(Mono/Flux)` ↔ `Subscriber` 固定 4 个信号：

- `subscribe()`：下游说 “我要订阅你”
- `request(n)`：下游告诉上游：**我现在最多能处理 n 条数据**（背压！）
- `onNext(T)`：上游按下游的能力，推送数据
- `onComplete / onError`：结束 / 异常

👉 重点：**下游有话语权，可以控制上游的发送速率**。上游不能自顾自猛发。

Mono、Flux 就是这个契约的载体；Sinks 是用来把非响应式回调，接入这套契约的适配器。

## 3. 对比表（好记）

表格

|维度|非响应式（同步 / 普通回调）|响应式（Reactor Mono/Flux）|
|---|---|---|
|数据发起方式|调用方主动拉；或者上游无节制推送|下游先订阅，下游通过 `request()` 控制上游推送速度|
|背压|无标准背压，自己写缓冲限流|内置标准化背压协商|
|错误、结束信号|异常靠 try-catch，回调没有统一结束信号|统一 `onError / onComplete` 信号|
|编程风格|命令式为主；回调地狱|声明式链式，描述流而不是一步步调度|
|线程|阻塞等待，或者回调线程随便切|线程模型和流解耦，调度器 Scheduler 单独控制|
|代表|普通接口、Callable、Future、Netty 原生回调|Mono、Flux、R2DBC、WebClient|

## 4. 用你熟悉的 Sinks 场景串起来

你有一个老的 Netty 回调（非响应式）：消息来了就进回调，消息疯狂涌入，它根本不知道你处理不处理得过来。 于是你用 `Sinks.Many` 做桥：

- 回调收到消息 → `sink.tryEmitNext()`（命令式，把数据塞进去）
- sink 内部遵守 Reactive Streams 契约，对外给一个 Flux
- 下游订阅 Flux，通过背压告诉上游：我处理不过来，慢点发

> 这就是：**把非响应式的事件，适配进响应式契约里**

## 5. 一个非常容易踩的误区

✅ 异步 = 不阻塞线程 ✅ 响应式 = 异步 + **标准化背压流契约**

> 很多人以为 WebFlux 只是异步非阻塞，其实它的灵魂是这套流契约；如果只是异步回调，那早就有了，不需要 Reactor。

## 6. 极简总结版（方便记笔记）

- 非响应式：我喊你给我数据，或者你随便扔给我，我自己扛压力；
- 响应式：我订阅你，我告诉你我能接多少，你再发给我，双方按约定的信号沟通。



关于回调地狱
# 回调地狱（Callback Hell）

一句话：**回调里面嵌套回调，一层套一层，代码向右不断缩进，像金字塔，可读性极差、很难处理异常、很难顺序控制，就是回调地狱。** 它属于**非响应式老式异步回调**的典型痛点，刚好和前面聊的响应式、声明式做对照。

> 核心根源：异步回调是 “事件来了才执行”，如果你需要**按顺序执行多个异步任务**，就只能把下一个异步写在上一个的回调里面。

## 举个 Java 里你能看懂的例子（Netty / 老异步 SDK 风格，贴近你平时接触的）

假设需求：

1. 异步请求 A：获取用户 id
2. 拿到用户 id 之后，异步请求 B：查询该用户订单
3. 拿到订单号之后，异步请求 C：查询订单明细
4. 最后打印明细

老式回调写法：

```
// 伪代码，模拟老的异步回调接口
asyncGetUserId(userIdResult -> {
    if (userIdResult.isSuccess()) {
        Long uid = userIdResult.getData();
        asyncGetOrderByUserId(uid, orderResult -> {
            if (orderResult.isSuccess()) {
                String orderNo = orderResult.getData();
                asyncGetOrderDetail(orderNo, detailResult -> {
                    if (detailResult.isSuccess()) {
                        System.out.println("订单明细：" + detailResult.getData());
                    } else {
                        System.err.println("查询明细失败");
                    }
                });
            } else {
                System.err.println("查询订单失败");
            }
        });
    } else {
        System.err.println("获取用户ID失败");
    }
});
```

你看问题：

- 不断向右缩进，越写越深，金字塔形状
- **异常分散在每一层里面**：每一层都要单独写失败分支，想统一捕获异常非常麻烦
- 想改成并行、跳过某一步、重试、超时，代码会疯狂膨胀
- 想提前 return、抽离逻辑很难；调试栈信息也很乱

这就是**回调地狱**。

> 经典 JS 版本（网上最常见的，方便你建立印象）

```
getUserId((uid) => {
  getOrder(uid, (order) => {
    getDetail(order.orderNo, (detail) => {
      console.log(detail);
    }, err3=>{});
  }, err2=>{});
}, err1=>{});
```

## 回调地狱的 4 个典型痛点

1. **缩进爆炸**，代码向右漂移，阅读困难
2. **异常割裂**：每一层回调单独处理 error，很难统一异常处理
3. **流程控制难**：循环、重试、超时、并行、取消都很难写
4. **变量作用域嵌套混乱**，内层可以直接访问外层变量，容易出隐蔽 bug

---

## 对比：几种方案怎么解决它

### 1. 先用 CompletableFuture（Java 原生异步，比回调好，但还不是响应式）

```
CompletableFuture<Long> f1 = asyncGetUserId();
CompletableFuture<String> f2 = f1.thenCompose(uid -> asyncGetOrderByUserId(uid));
CompletableFuture<Detail> f3 = f2.thenCompose(orderNo -> asyncGetOrderDetail(orderNo));
f3.whenComplete((detail, ex) -> {
    if (ex != null) {
        System.err.println("统一异常：" + ex.getMessage());
    } else {
        System.out.println(detail);
    }
});
```

✅ 链式，不再嵌套；异常可以统一捕获。

> 但它只能处理**单个结果**，不适合流式多条数据，没有背压。

### 2. 再看 Reactor Mono（响应式，就是你前面学的）

```
asyncGetUserIdMono()
    .flatMap(uid -> asyncGetOrderMono(uid))
    .flatMap(orderNo -> asyncGetDetailMono(orderNo))
    .doOnSuccess(detail -> System.out.println(detail))
    .doOnError(err -> System.err.println("统一异常：" + err))
    .subscribe();
```

✅ 同样链式声明式；额外自带：背压、调度器切换、超时、重试、限流、SSE 流式支持。

> 这也是为什么 WebFlux / Reactor 推崇这种写法，避开回调地狱。

### 3. 补充：Sinks 是干嘛的？

如果你的底层只能拿到老式回调（Netty、老 SDK 回调），你不得不用回调，那就用 Sinks 在回调里 `emitNext`，把回调事件喂进 Flux/Mono，**把地狱回调封装成干净的响应式流**。

## 帮你串整条链路（笔记版）

1. 原始：同步阻塞 → 简单，但是卡线程
2. 早期优化：异步回调 → 不卡线程，但顺序依赖时产生**回调地狱**
3. Java 后续：CompletableFuture → 链式异步，解决回调地狱（单结果）
4. 响应式：Reactor Mono/Flux → 声明式链式 + 背压 + 流式能力
5. 桥接：Sinks → 把老回调（回调地狱来源）转成 Flux/Mono

> 一句话总结： 回调地狱不是 “异步不好”，是**用嵌套回调表达串行依赖的异步逻辑，写法天然丑陋**
